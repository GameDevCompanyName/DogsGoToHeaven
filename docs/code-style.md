# Все псы попадают в рай — код-стайл и рабочий процесс

Свод правил разработки. Файл лежит в `docs/code-style.md`. Короткая выжимка с командами — в `CLAUDE.md` в корне. Что строим, описано в `docs/prd.md`.

## Архитектура: Feature-Sliced Design

Проект строится по FSD. Слои сверху вниз: `app`, `pages`, `widgets`, `features`, `entities`, `shared`.

- Слой импортирует только из слоёв ниже себя. Слайсы одного слоя друг друга не импортируют.
- Каждый слайс отдаёт публичный API через `index.ts`. Импорт в обход публичного API запрещён.
- Сегменты внутри слайса: `ui`, `model`, `lib`, `api`, `config`. Лишние сегменты не создаём.
- Нарушения ловит Steiger, его ошибки исправляются так же, как ошибки ESLint.

### FSD внутри SvelteKit

- Все слои лежат в `src/`, импортируются через алиасы `@/app`, `@/pages`, `@/widgets` и так далее. Алиас `$app` занят SvelteKit, для слоя `app` его не используем.
- `src/routes` — тонкий: `+page.svelte` только импортирует и рендерит страницу из слоя `pages`. Логики в роутах нет.
- Компоненты shadcn-svelte живут в `shared/ui`. Правим их только когда без этого нельзя.

### Движок ранжирования

Отдельный модуль в `shared/lib/ranking`. Чёрная коробка для остального проекта:

- Чистые функции от датасета, весов и состояния фильтров. Никаких рун, никаких импортов из Svelte и из других слоёв.
- Наружу через `index.ts` торчит только публичный API: типы входа и выхода и функции ранжирования.
- Нормализация, перераспределение весов при пропусках и фильтры — внутри модуля.
- Реактивная обёртка над движком живёт выше, в `entities` или `features`, и только вызывает его.

## Svelte 5

Только руны. Legacy-синтаксис Svelte 3 и 4 не используется нигде: ни `$:`, ни `export let`, ни `on:click`, ни слотов.

- `$state` — только для значений, которые двигают интерфейс. Остальное — обычные переменные.
- `$derived` — для всего, что вычисляется из других значений.
- `$effect` — последнее средство, только для синхронизации с внешним миром, например с MapLibre. Каждое использование сопровождается комментарием, почему нельзя через `$derived`. Менять состояние внутри `$effect` запрещено.
- Разделяемое состояние — реактивные классы в файлах `*.svelte.ts`, а не сторы из `svelte/store`.
- Вместо слотов — сниппеты и `{@render}`.
- События — колбэк-пропсы: `onselect`, `onchange`. `createEventDispatcher` не используем.

### Порядок в блоке script

Одинаковый во всех компонентах:

1. Импорты.
2. Типы, включая `interface Props`.
3. `$props`.
4. `$state`.
5. `$derived`.
6. Функции и обработчики.
7. `$effect`.

```svelte
<script lang="ts">
  import { Button } from '@/shared/ui/button';
  import type { City } from '@/entities/city';

  interface Props {
    city: City;
    onselect: (id: string) => void;
  }

  let { city, onselect }: Props = $props();

  let isExpanded = $state(false);

  const scoreLabel = $derived(city.score.toFixed(1));

  function handleClick() {
    onselect(city.id);
  }
</script>
```

### Реактивный класс

```ts
// ranking-store.svelte.ts
export class RankingState {
  weights = $state<Weights>(DEFAULT_WEIGHTS);
  filters = $state<Filters>({});

  results = $derived(rank(cities, this.weights, this.filters));

  setWeight(factor: FactorId, value: number) {
    this.weights[factor] = value;
  }
}
```

## TypeScript

- `strict: true`. `any` запрещён, `unknown` с последующим сужением допустим.
- Типы факторов и датасета — единый источник правды, от него пляшут и движок, и интерфейс.
- `type` для объединений и данных, `interface` для пропсов и публичных контрактов.
- Только именованные экспорты. Исключение — компоненты Svelte.
- Никаких `as` для заглушки ошибок. Если без приведения нельзя — комментарий почему.

## Именование

- Файлы и папки — `kebab-case`: `city-card.svelte`, `normalize-percentile.ts`.
- Компоненты в разметке и типы — `PascalCase`.
- Функции и переменные — `camelCase`, константы уровня модуля — `UPPER_SNAKE_CASE`.
- Булевы значения — с префиксом `is`, `has` или `should`.
- Обработчики внутри компонента — `handleX`, колбэк-пропсы — `onx`.

## Стили

- Tailwind, классы сортирует `prettier-plugin-tailwindcss`.
- Условные классы — через хелпер `cn` из shadcn-svelte.
- `<style>` в компонентах — только когда на Tailwind не выразить.
- Мобильная вёрстка обязательна: сначала телефон, потом десктоп.

## Тесты

Без фанатизма, покрываем только то, что того стоит.

- **Vitest** — юнит-тесты на тяжёлую бизнес-логику и чистые функции. Движок ранжирования, нормализация, перераспределение весов, фильтры — обязательно. Тест лежит рядом с кодом: `rank.ts` и `rank.test.ts`.
- **Playwright** — только ключевые сценарии в `tests/e2e`: карта рендерится, ползунок меняет выдачу, карточка города открывается.
- Интерфейс за пределами этих сценариев не тестируем. Тесты на то, что Svelte рендерит разметку, не пишем.
- Тест короткий: одна проверка — одна идея, данные — минимальный выдуманный датасет.

## Линтеры и проверки

- ESLint с `eslint-plugin-svelte` и `typescript-eslint`, включая сортировку импортов.
- Prettier с плагинами для Svelte и Tailwind.
- `svelte-check` — типы в `.svelte` файлах.
- Steiger — архитектура FSD.
- commitlint — формат коммитов.

Команда `npm run verify` прогоняет всё сразу: форматирование, ESLint, Steiger, `svelte-check`, Vitest и Playwright.

**После каждой фичи и каждого заметного изменения прогоняется `npm run verify`. Все ошибки и предупреждения исправляются до коммита, а не «потом».** Отключать правило линтера комментарием можно только с объяснением в том же комментарии.

## Инструменты

- Менеджер пакетов — npm.
- husky плюс lint-staged: на `pre-commit` — Prettier и ESLint по изменённым файлам, на `commit-msg` — commitlint.
- CI на GitHub Actions: `npm run verify` на каждом пул-реквесте.

## Git-процесс

- `main` защищена: прямой пуш запрещён, мерж только через пул-реквест с зелёным CI.
- Одна фича — одна ветка: `feat/ranking-engine`, `fix/map-zoom`.
- Коммиты — Conventional Commits: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `ci`. Описание на английском, в повелительном наклонении: `feat(ranking): add percentile normalization`.
- Пул-реквест — это точка ревью и история решений. В описании три блока: что сделано, почему так, как проверить.
- Чейнджлог генерируется автоматически из коммитов через release-please: после мержа в `main` он ведёт релизный пул-реквест с обновлённым `CHANGELOG.md`. Changesets не используем: он про версионирование пакетов, а мы не библиотека.
