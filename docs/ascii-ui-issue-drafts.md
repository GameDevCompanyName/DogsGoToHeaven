## 1. Input: добавить явное состояние наведения

**Тип:** недостающая возможность взаимодействия; отсутствие отдельного hover подтверждено исходниками. **Приоритет:** обычный, без доказанного нарушения доступности. Задача потребителя — распознать поле поиска/фильтра до фокуса. Компонент: Input s, Phosphor.

**Публичный пример:**

```svelte
<script>
  import { Theme, Input } from 'svelte-ascii-ui';
</script>

<Theme palette="phosphor">
  <Input size="s" aria-label="Найти город" placeholder="Название города" />
  <Input size="s" aria-label="Недоступный поиск" disabled />
</Theme>
```

**Шаги:** без CSS приложения навести мышь на первое поле, убрать указатель, затем перейти в него Tab; сравнить с disabled. **Ожидается:** отличимое наведение без изменения геометрии, отдельное от фокуса и ошибки. **Фактически по коду:** Input использует `.aui-control`; в `dist/theme.css` есть focus-visible, invalid и disabled, но нет hover для этого класса. Это не утверждение об отсутствии фокуса.

**Диагноз:** size и Theme.colors не добавляют состояние взаимодействия. Panel может отделить фон поля от окружения, но не решает hover. Патч внутренних селекторов не вводился; состояние принадлежит UIKit. Связанный consumer-кадр: настройки; изолированного кадра нет.

**Приёмка:** показать default/hover/focus/invalid/disabled для s/m во всех трёх палитрах; hover не маскирует invalid/focus и не активируется у disabled; нет сдвига размеров. Проверить родственные поля, использующие `.aui-control`, чтобы общее правило не меняло их случайно. Направление — согласованное состояние UIKit, конкретный цвет не предписан.

## 2. Checkbox: добавить обратную связь при наведении на всю подпись

**Тип:** недостающая возможность взаимодействия; отсутствие отдельного hover подтверждено. **Приоритет:** обычный. Сценарий — выбор фильтра; Checkbox s, Phosphor.

```svelte
<script>
  import { Theme, Checkbox } from 'svelte-ascii-ui';
</script>

<Theme palette="phosphor">
  <Checkbox size="s" label="Только подходящие города" />
  <Checkbox size="s" label="Выбрано" checked />
  <Checkbox size="s" label="Часть группы" indeterminate />
  <Checkbox size="s" label="Недоступно" disabled />
</Theme>
```

**Шаги:** навести на mark и текст каждого варианта; затем Tab и Space. **Ожидается:** вся область выбора даёт согласованную обратную связь; состояния выбора и клавиатурный фокус различимы. **Фактически по коду:** `Checkbox.svelte` задаёт checked/indeterminate, focus-visible и disabled; hover отсутствует и в компоненте, и в общих правилах `.aui-control`. Невидимый нативный input покрывает label, поэтому нельзя ограничивать будущий hover только нарисованным mark.

**Диагноз:** смена размера/палитры не добавляет hover. Размер mark и отрисовка состояния — ответственность UIKit; новая предметная обёртка не нужна. Обхода через CSS нет. Контекст: кадр настроек; отдельного воспроизведения в браузере нет.

**Приёмка:** наведение на текст и mark одинаково работает для unchecked/checked/indeterminate; disabled не выглядит активным; Space, фокус и нажатие на label сохраняются. Проверить s/m, три палитры, coarse pointer и forced colors. Не уменьшать область нажатия ради компактности.

## 3. Button / Progress: описать прозрачные поверхности и поддерживаемую композицию

**Тип:** вопрос дизайна и документации, не подтверждённый дефект. **Приоритет:** низкий. Сценарий — различить действие и шкалу среди плотных настроек. Button s/default и primary, Progress s/value=0.4, Phosphor.

```svelte
<script>
  import { Theme, Button, Progress, Panel } from 'svelte-ascii-ui';
</script>

<Theme palette="phosphor">
  <Button size="s" label="Применить" />
  <Button size="s" variant="primary" label="Выбрать" />
  <Progress size="s" value={0.4} label="Заполнение бюджета" />
  <Panel size="s">
    <Button size="s" label="Применить в панели" />
    <Progress size="s" value={0.4} label="Заполнение в панели" />
  </Panel>
</Theme>
```

**Шаги:** сравнить компоненты на фоне страницы и Panel, затем hover/focus Button. **Ожидается:** понятный рецепт выбора поверхности; если нужна самостоятельная заливка, поддерживаемый способ её запросить. **Фактически:** `.aui-button` прозрачен в покое; primary меняет цвет текста/рамки, а не даёт постоянную заливку. Hover имеет полупрозрачную заливку, focus — отдельный фон. `Progress.svelte` явно задаёт `background:transparent`; публичные props — value, label, size, отдельного фона дорожки нет. Это действующий дизайн ASCII-компонентов.

**Диагноз:** Panel/фон внешней области решают группировку на уровне приложения, но не являются самостоятельным вариантом дорожки Progress. Менять геометрию/фон внутренних элементов нельзя считать обычной интеграцией. Обходов не добавлено. Кадры старта/настроек — только контекст, не доказательство нечитаемости.

**Приёмка:** документация и пример показывают покой/hover/focus/disabled/loading Button, Progress 0/0.4/1 на странице и в Panel, s/m и все палитры. Явно описана намеренная прозрачность. Если композиции недостаточно для принятого сценария, отдельно согласовать публичную настройку поверхности с сохранением текущего default. Не требовать глобальной заливки по одному скриншоту.

## 4. Input / Theme: объяснить совпадение фона поля с фоном страницы

**Тип:** вопрос дизайна и документации. **Приоритет:** низкий; не смешивать с issue 1 про hover. Задача — визуально выделить поиск без внутренних CSS-патчей.

```svelte
<script>
  import { Theme, Input, Panel, palettes } from 'svelte-ascii-ui';
</script>

<Theme palette="phosphor">
  <div style:background={palettes.phosphor.background}>
    <Input size="s" aria-label="Поиск на странице" />
    <Panel size="s">
      <Input size="s" aria-label="Поиск внутри панели" />
    </Panel>
  </div>
</Theme>
```

**Шаги:** сравнить два поля в покое и фокусе. **Ожидается:** документированный способ разделить поверхности. **Фактически:** `.aui-control` использует `--bg`; если приложение выбирает `palettes.phosphor.background` для страницы, значения совпадают. Theme сам не назначает фон всей страницы. Panel использует смесь text 3.5% и bg, поэтому окружение поля отличается. Это выбор ролей палитры, не ошибка применения `surface`.

**Диагноз:** Theme.colors.background меняет общий семантический фон контролов/overlays; это не независимая настройка Input. Приложение уже размещает поле в Panel. Не предлагаем менять глобальную палитру ради одного поля. Контекст — настройки; измерений различимости нет.

**Приёмка:** добавить пример «страница → Panel → Input» и пояснение ролей background/surface, включая влияние на overlays; показать три палитры. Если поддерживается отдельная поверхность полей, описать её публичный контракт и проверить связанные контролы. Принятие документированного текущего дизайна также решает вопрос.

## 5. Popover: поддержать компактный триггер пояснения внутри строки

**Тип:** недостающая возможность. **Приоритет:** обычный. Сценарий — пояснение рядом с названием метрики в плотном разборе города. Popover s, Phosphor.

```svelte
<script>
  import { Theme, Popover } from 'svelte-ascii-ui';
</script>

<Theme palette="phosphor">
  <div>
    Стоимость жизни
    <Popover size="s" label="Как рассчитана стоимость жизни">
      {#snippet trigger()}<span aria-hidden="true">?</span>{/snippet}
      <p>Оценка расходов за месяц для выбранного состава семьи.</p>
    </Popover>
  </div>
</Theme>
```

**Шаги:** открыть пояснение мышью и клавиатурой, оценить высоту строки; повторить на узком экране и coarse pointer. **Ожидается:** поддерживаемый inline/compact способ показать краткий маркер без потери доступного имени и удобной области нажатия. **Фактически:** публичный `trigger` snippet существует, но рисуется **внутри штатного button** с `.aui-button`; это не возможность заменить корень произвольным триггером. Size ограничен s/m; CSS задаёт минимум 36/48px, для coarse pointer — минимум 44px. Это значения правил, а не замеры конкретного кадра.

**Диагноз:** короткий label, snippet и size=s не устраняют минимальную геометрию. Приложение может вынести подсказку на отдельную строку и настроить внешние интервалы; это допустимая текущая композиция. Уменьшение внутренних размеров не вводилось. Контекст — карточки города; перенос не доказывает дефект размещения overlays.

**Приёмка:** пример плотной кириллической строки с публичным compact/inline API либо явно рекомендованной композицией; Tab, Enter/Space, Escape, возврат фокуса, accessible name и aria-expanded сохраняются. Проверить края viewport, длинный текст, s/m и coarse pointer; компактный вид не должен автоматически означать уменьшенную область нажатия. Обязательные инструкции остаются рядом с полем, а не только в Popover.

## 6. Badge / Panel / Separator: дать рецепт оценки и структурных границ

**Тип:** документация по композиции. **Приоритет:** низкий. Сценарий — общий балл и группы положительных/отрицательных факторов; ответственность за раскладку остаётся у приложения.

```svelte
<script>
  import { Theme, Badge, Panel, Separator } from 'svelte-ascii-ui';
</script>

<Theme palette="phosphor">
  <p>Общий балл: <Badge size="m" tone="success">82 / 100</Badge></p>
  <p>Относительно других городов: <Badge size="m">Выше среднего</Badge></p>
  <Panel size="s" title="Повышают оценку"><p>Умеренная аренда</p></Panel>
  <Separator />
  <Panel size="s" title="Понижают оценку"><p>Высокие расходы на транспорт</p></Panel>
</Theme>
```

**Шаги:** прочитать оценку, её шкалу и две группы на широком/узком экране; сравнить размер s/m и длинные подписи. **Ожидается:** рецепт, различающий метку, числовую оценку и структуру страницы. **Фактически:** Badge — текст со скобками, tone и size, без appearance/filled/outline prop; m использует .85em, s — .75em. Panel и Separator уже дают структурные рамки/пунктир. Design guide советует тихие структурные границы и избегать лишних вложенных рамок, но конкретного рецепта балла и шкал нет.

**Диагноз:** текущий consumer уже использует Badge для score; отдельный компонент Score и новый вариант заливки не обязательны. Семантику абсолютной/относительной оценки передаём подписью, а не только цветом. Пунктирные границы прикладной таблицы, группировка факторов, footer вне прокручиваемого Panel и палитра карты/таблицы принадлежат приложению. Panel.footer сам по себе не обещает закрепления при прокрутке всей панели. Историческое требование заполненного Badge из старого отчёта — необязательное пожелание, не блокер. Внутренних патчей нет; контекст — город/сравнение.

**Приёмка:** добавить публичный пример Badge с числом и подписью шкалы, Panel для групп, Separator для связанных секций; показать длинный русский текст, 390px, s/m, все tones. Объяснить, когда достаточно заголовка/пространства и как приложение размещает постоянные действия вне scroll-области. Не обещать filled/outline без отдельного дизайн-решения; не перекладывать продуктовую раскладку на UIKit.

## 7. Необязательно: Drawer / Dialog — нижнее открытие и размеры окна

**Тип:** недостающие возможности, не регрессия. **Приоритет:** низкий, отдельный backlog; не условие принятия текущей миграции. Сценарий — длинный обзор города и сравнение; существующие Drawer справа и Dialog на телефоне приняты как композиция.

```svelte
<script>
  import { Theme, Button, Drawer, Dialog } from 'svelte-ascii-ui';
  let cityOpen = $state(false);
  let comparisonOpen = $state(false);
</script>

<Theme palette="phosphor">
  <Button label="Город" onclick={() => (cityOpen = true)} />
  <Button label="Сравнить" onclick={() => (comparisonOpen = true)} />
  <Drawer bind:open={cityOpen} side="right" size="l" title="Город" closeLabel="Закрыть">
    <p>Длинный обзор города</p>
  </Drawer>
  <Dialog bind:open={comparisonOpen} size="xl" title="Сравнение" closeLabel="Закрыть">
    <p>Сравнение трёх городов</p>
  </Dialog>
</Theme>
```

**Шаги:** открыть по очереди; проверить на ширинах 390/768/1024/1280/1440px, затем заменить текст длинным обзором. **Ожидаемая возможность:** явно поддерживаемое нижнее открытие и настройка размеров, если продукт вновь потребует прежнюю геометрию. **Фактически:** Drawer.side — только left/right; размеры s/m/l/xl соответствуют 25/33/50/67vw. Dialog имеет s/m/l/xl/fit и внутренние ограничения высоты; именованных props размеров окна/нижнего открытия нет. При 1440px 67vw = 964.8px, при 1024px 50vw = 512px — расчёт из CSS, не измерение и не дефект относительно прежних 880/440px.

**Диагноз:** HTML class/style принимаются корнем Dialog и через Drawer; поэтому нельзя утверждать, что любое изменение размера публично невозможно. Не хватает документированного адаптивного контракта; внутренний `--overlay-width` не объявлен публичным токеном. Приложение выбирает size по breakpoint и Dialog на телефоне. Нижнее открытие этим не появляется; CSS-патчи не вводились. Фиксированный footer обычного Panel сюда не относится. Контекст — город на телефоне/десктопе и сравнение, не изолированные измерения.

**Приёмка:** сначала документировать допустимую настройку размеров через публичный API; при принятии нижнего Drawer добавить отдельный пример с длинным телом и видимым footer. Проверить указанные ширины, горизонтальный overflow сравнения, Escape, Tab, возврат фокуса, экранную клавиатуру; существующие left/right и размеры сохраняются. Это два независимо принимаемых расширения; при реализации разнести в две задачи.

### Отдельная необязательная документационная задача: Dialog рядом с Tailwind Preflight

**Тип:** интеграционная документация, не доказанная поломка модального поведения. **Ожидается:** центрированное обычное окно при подключённом reset. **Фактически по старому consumer-отчёту:** Preflight обнулял margin; Dialog не восстанавливает его явно, в отличие от позиционирования Drawer.
